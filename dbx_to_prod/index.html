Mariner GenAI: trial → prod migration guide

How to recreate the Mariner employee-assistance system (agents, indexes, data, settings and app) in a new production Databricks account.

Built from a read-only export of the trial workspace dbc-957e994b-63c5 on 2026-10-23. Every name, setting and row count below comes from that export.

Updated 2026-10-28 with Coaching360 (the /coaching360 chat, its data and agents). Those parts come from the repo sources that built them in trial (coaching360/), not from exports/, which predates them.

1. What is being moved

The system answers employee questions about branch operations, the employee handbook, benefits and performance management, with verified sources. It has two kinds of agents:

  • Agent Bricks agents (managed, configured not coded): three Knowledge Assistants, one Genie space and the Supervisor that routes between them.
  • Custom code agents (MLflow models you log and serve): perf_policy_citations_agent, which returns Employee Performance Policy answers with registry-backed citations.
  • Coaching360 (app-directed): /coaching360 picks a person, the app finds their level (employee, branch or district) and sends the Supervisor a routing directive. The Supervisor then uses only that level's Genie space or the Coaching360 Guide assistant. Each Genie space reads a c360_<level> schema whose views return only the rows the person may see.

The chunk tables (four, five with coaching360_chunks) feed Delta Sync indexes that sync all columns. Never ALTER their schema or bulk-UPDATE them by hand: that forces a full re-sync and can break Knowledge Assistant retrieval. Change documents in the volume and re-run notebooks 03 and 04 (or the upload tool) instead.

How documents become indexes

  1. Parse (ai_parse_document, v2.0): only PDFs whose content or location is new. A moved or renamed PDF reuses its earlier parse, so it costs nothing and keeps the same chunk ids. This fix is in both notebook 03 and simple_upload/app.py.
  2. Elements: latest parse of each file still in the volume; if the same PDF sits in two folders, only the newest copy is used, so chunk ids stay unique.
  3. Chunks: about 3,500 characters per chunk within a page, with embedding_text = "Document: …\nPage: …\n\n" + text. Truncate and insert, so the change data feed drives the index sync.
  4. Performance policy: one chunk per page into app_policy_chunks; then sql/08 approves only passages that match the citation registry exactly once (9 in trial) into perf_policy_retrieval.
  5. Coaching360 BRD: the same four steps as the other domains, from agents/agent_bricks/coaching360/brd_pipeline_steps.json.
  6. Sync the TRIGGERED indexes (notebook 04 or the upload tool's refresh button).

7. Custom code agents

7.1 perf_policy_citations_agent (migrate)

  • What it does: retrieves the top 5 passages from perf_policy_retrieval_index, asks databricks-claude-haiku-4-5 to answer and pick passage labels, then builds citation objects in code from the retrieved metadata. It returns {"answer", "citations"} JSON, which the app validates against app_citation_registry.
  • Type: MLflow ResponsesAgent, models-from-code (agents/custom/perf_policy_citations_agent/perf_policy_citations_agent.py), with streaming support.
  • Prod name: model workspace.performance_test.perf_policy_citations_agent (trial: workspace.ask_mariner_perf_dev… v2), endpoint perf-policy-citations.
  • Deploy: notebook 05 logs it with resources for the index and the model endpoint (automatic auth passthrough, no tokens), registers it in Unity Catalog, tests it locally and deploys with databricks.agents.deploy(…, scale_to_zero=True).
  • Change the code later: edit the .py file, re-run notebook 05 (it registers a new version and updates the endpoint). Keep INDEX and LLM_ENDPOINT in the file in line with 00_config; the notebook stops if they differ.

7.2 benefits_agent (do not migrate)

This agent has no retrieval step. agents/custom/benefits_agent/agent.py sends the question with a system prompt to databricks-claude-sonnet-4-5 and returns the reply. No knowledge base or tool is attached, so answers come from the model's own knowledge, and its Source: lines are not grounded. This matches the trial symptoms ("documentation does not provide enough information" for PTO; failed citation lookups for PPO). In prod, the Supervisor and /benefits use the mariner-benefits-assistant Knowledge Assistant instead. Notebook 05 can still deploy the old agent behind DEPLOY_LEGACY_BENEFITS = True if something else depends on it.

8. The Flask app

  1. Create a Databricks App (compute Medium, as in trial) from the Git folder. Copy dbx_to_prod/app/app.yaml to the source root.
  2. Add app resources: sql-warehouse (Can use), supervisor-endpoint (Can query) and session-secret (a secret with 32+ random characters).
  3. Paste the DIRECT_SPECIALIST_ROUTES_JSON line printed by notebook 06 into app.yaml. Check every value against app/env.prod.template. Make sure DATABRICKS_HOST resolves to an https:// URL; the app requires it.
  4. Give the app's service principal Can query on the KA endpoints and perf-policy-citations, and Can run on the Genie spaces (notebooks 05 and 06 do this when APP_SP is set). For Coaching360 it also needs the grants in sql/coaching360/05b_demo_grants_app.sql (notebook 02b): the level views and functions, user_map (read and write) and the three directory tables for the name lookup.
  5. Deploy. Open the app: a free-form question should show a progress message within about 5 seconds and then a cited answer.
COACHING360_ENABLED ships false. Everything it needs is built by the notebooks, but the chat's persona model is demo-only (§11). Set it to true, with COACHING360_TIMEOUT_SECONDS at or below GUNICORN_TIMEOUT_SECONDS, only after that is fixed or for a closed pilot.
PERFORMANCE_FAST_PATH_ENABLED stays false in prod. The fast path reads employee data with the app's identity instead of the signed-in manager's, so the app refuses to start it when APP_ENV=production. Turning it on needs per-manager access scoping first.

FROM system.billing.usage

ORDER BY usage_date DESC, dbus DESC;

If cold starts matter more than cost

Instead of turning scale-to-zero off all day, schedule a job that turns it off at the start of business hours and back on in the evening (serving_endpoints.update_config). Measure first: in trial, cold starts mostly affected the custom endpoint (p50 72 s through the Supervisor).

10. Validate and cut over

Automated

Set the endpoint names in 07_validate, then Run all. It checks row counts, the Coaching360 schemas, data_status, people per level, Genie spaces and Supervisor tools, materialized views against the live views, chunk counts, index readiness and row counts, index pipeline type, endpoint scale-to-zero, sample answers from each specialist and the Supervisor, and warehouse settings.

Manual (in the prod app)

Cut over and roll back

  1. Run both systems side by side; compare answers for the questions above.
  2. Point users to the prod app URL. Keep the trial app stopped but intact for one release cycle.
  3. Roll back by sending users to the trial app (until the trial account expires). To roll back a single agent in prod, re-create it from the files in agents/ or, for the Genie space, PATCH it with serialized_space_live_views.json.
  4. After sign-off: drop workspace.performance_test.migration_staging in prod and trial.

Keeping documents current after go-live

Add, replace, move or delete PDFs in the domain's volume (sub-folders are fine), then run notebooks 03 and 04, or the upload tool's refresh for that domain only. Moving a file needs no other action: its parse is reused and its chunk ids stay the same.
